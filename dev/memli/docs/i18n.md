# Internationalization (i18n) & localization

**Related:** [roadmap.md](./roadmap.md) · [architecture.md](./architecture.md) · [product-ux.md](./product-ux.md) · [mobile.md](./mobile.md)

Full Sail’s guidance is right: **plan early**, implement in layers — not a last-minute string scrape. This product’s second major market is expected to be **Latin America**, which shapes locale priority without requiring every regional variant on day one.

---

## Two different “languages” (critical)

A language-learning product must never collapse these into one field:

| Concept | Meaning | Example |
| --- | --- | --- |
| **UI locale** | Language of app chrome (buttons, settings, errors) | User interface in Latin American Spanish |
| **Learning language** | Language / pair being studied | Studying Japanese vocabulary (with Spanish or English glosses, etc.) |
| **Content locale** | Language of a deck, card, or mnemonic community post | A mnemonic written for Spanish speakers learning English |

### Product consequences

- Settings need **independent** controls (at least: UI language vs what I’m studying).
- APIs and schemas must not use a single `language` everywhere without qualifiers (`uiLocale`, `learningLanguage`, `contentLocale`, etc.).
- Analytics should distinguish “Spanish UI users” from “users learning Spanish.”

If you only remember one i18n rule for this codebase, remember this separation.

## Target locales

### Phase 2 primary pair

| Tag | Use |
| --- | --- |
| `en` | Default / initial UI and much early content |
| `es-419` | Latin American Spanish UI (and eventually marketing) |

[`es-419`](https://www.unicode.org/cldr/) is the standard region code for Latin America & Caribbean Spanish. It avoids prematurely committing to `es-MX` vs `es-AR` wording.

### Later candidates

| Tag | When to consider |
| --- | --- |
| `pt-BR` | If Brazil is confirmed as a top market — **Portuguese**, not Spanish |
| Specific `es-MX`, `es-CO`, … | Only if community feedback shows `es-419` is insufficient |

### Explicitly not early goals

- Full UI in dozens of languages
- Dialect-perfect marketing for every country
- RTL languages (not needed for `en` / `es` / `pt`) — but avoid CSS that would make RTL impossible forever if you expand much later

## What to do now (Phase 1 prep — no library required)

These habits are cheap and prevent rewrites:

### 1. Keep domain logic free of UI copy

`packages/core` (SRS grading, etc.) must not return English sentences for UI. Return structured results; let clients localize.

### 2. Prefer API error codes

```text
Good:  { "error": { "code": "INVALID_CREDENTIALS" } }
Bad:   { "error": "Invalid email or password." }  // only English, hard to i18n centrally
```

Clients map `INVALID_CREDENTIALS` → localized string. Optional English `message` for logs is fine if `code` is authoritative.

### 3. Avoid string concatenation for sentences

```text
Bad:  "Hello, " + name + "!"
Good: one message template with a placeholder, e.g. "Hello, {name}!"
```

Plural rules differ by language (“1 card” / “5 cards”). When you add an i18n library, use its plural features; until then, avoid clever English-only plural hacks in shared code.

### 4. Plan content language on learning entities

Even before UI i18n ships, new schema designs for decks, cards, and mnemonics should include a **content language / locale** (name TBD in schemas). Community content for LATAM will not all be English.

### 5. Store instants in UTC; format with `Intl`

- Persist ISO-8601 / Unix timestamps
- Display with `Intl.DateTimeFormat`, `Intl.NumberFormat` using the active UI locale
- Do not hard-code `MM/DD/YYYY` assumptions in shared formatters

### 6. UTF-8 everywhere

Assume names, mnemonics, and examples contain accents and non-ASCII (`ñ`, `á`, Japanese kana later, etc.). No legacy charset shortcuts.

### 7. HTML `lang`

When locale switching exists, set `document.documentElement.lang` (and Astro page `lang` in Phase 3) to the active UI locale.

## What to implement in Phase 2

### Library choice (decide at implementation)

Any modern approach is fine if it supports:

- Message catalogs per locale
- Interpolation + plurals
- Dev ergonomics with Vite / React
- Eventual reuse of message IDs on mobile (or parallel catalogs with the same keys)

Candidates to evaluate when the time comes (non-binding): FormatJS / `react-intl`, i18next, Paraglide, Lingui, etc. **Record the choice here** when picked:

| Decision | Choice | Date |
| --- | --- | --- |
| Web i18n library | _TBD_ | |

### Scope for first `es-419` ship

Translate **authenticated chrome** first:

- Auth (sign in, errors)
- Dashboard / navigation
- Study session controls and empty states
- Settings (including the language controls themselves)

Defer:

- Entire marketing site translation (pairs naturally with Phase 3 Astro)
- Every blog post
- Perfect legal translations (use professional help for privacy/terms)

### Locale selection UX

Priority order (suggested):

1. Explicit user preference (settings / first-run)
2. Otherwise `Accept-Language` / device locale guess
3. Fallback `en`

Never change UI locale mid-session without user action in a surprising way.

## Localization beyond words (LATAM)

“Localization” for Latin America is not only translation:

| Area | Guidance |
| --- | --- |
| Examples & imagery | Avoid US-only cultural references on marketing when targeting LATAM |
| Community mnemonics | Encourage / tag content by locale; discovery should filter sensibly |
| Pricing | If paid tiers appear, plan currency display and regional pricing separately from string catalogs |
| Tone | Prefer clear, respectful second-person copy; avoid slang that only works in one country when using `es-419` |
| Support | Spanish-capable support path is a product ops concern later |

## Marketing & SEO (Phase 3 alignment)

When Astro marketing exists:

- Localized routes such as `/es/` or `/es-419/` (exact scheme TBD) help acquisition
- Do not block the React app split on marketing i18n — but design URL strategy so English and Spanish marketing can coexist on `{brand}.com`
- Open Graph locale tags should match page language

Until then, English marketing is acceptable while app foundations ship.

---

## Mobile (Phase 4)

- Reuse the **same message keys** where practical, or generate catalogs from one source
- Respect OS language as a default signal; still honor server-stored UI locale after login
- `packages/schemas` carries locale fields; `packages/core` stays copy-free
- See [mobile.md](./mobile.md)

---

## Testing expectations

- Unit-test `packages/core` without locale
- When i18n lands: smoke-test critical flows in `es-419` (sign-in error, grade button labels, empty deck)
- Add a short checklist to QA for “UI Spanish + learning Japanese” (or similar) so the separation stays real

---

## Anti-patterns

- [ ] One `user.language` used for both UI and study target
- [ ] English sentences returned as the only API error form
- [ ] Interpolating by concatenating localized fragments in the wrong order
- [ ] Shipping `es` from Spain-specific copy for a LATAM-first push without review
- [ ] Blocking core feature PRs on full marketing translation
- [ ] Putting user-visible strings into `packages/core`
